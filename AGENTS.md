# Project YCG — Agent Instructions

## 1. Project Identity

**Project codename:** Project YCG  
**Full name:** YouTube Chapterization For Games

Project YCG is a local AI-assisted system for analyzing long-form gameplay videos and generating meaningful YouTube chapter suggestions.

The system is intended to work with very long gameplay recordings, including videos that may be **6–10 hours long** and games whose complete playthrough may span **tens or hundreds of hours across multiple video files**.

The project must support both:

- gameplay with commentary, webcam, or livestream interaction;
- gameplay without commentary.

The system should identify meaningful gameplay events such as bosses, locations, major encounters, progression events, and other recognizable moments and use them to produce useful chapter candidates.

## 4. Core Project Principle

Project YCG must primarily understand **what happens visually in the game**.

The transcript is not a sufficiently reliable representation of gameplay events.

### Transcript reliability rule

Never treat speech transcription as the authoritative source for gameplay event detection.

For commentary videos, the player may:

- talk about unrelated subjects;
- respond to chat;
- mention previous or future events;
- discuss another game;
- joke or speculate;
- name a boss before encountering it;
- refer to something that is not currently visible.

Therefore:

> Transcript information may be used as supporting evidence, but it must not be treated as the primary ground truth for gameplay understanding.

Any implementation that effectively reduces chapter detection to transcript analysis violates a core requirement of the project.

## 5. Evidence-Based Detection

Prefer evidence obtained directly from the video whenever practical.

Potential evidence sources include:

- sampled video frames;
- visual scene changes;
- UI elements;
- boss names;
- enemy appearance;
- location names;
- loading screens;
- menus;
- health bars;
- title cards;
- subtitles generated by the game itself;
- distinctive environments;
- cutscenes;
- recognizable gameplay states;
- OCR results where useful;
- temporal relationships between detected events.

Audio and transcript information may complement this evidence but should not override stronger visual evidence without a good reason.

Detection decisions should ideally be explainable through identifiable evidence.

---

## 6. Game Knowledge

The system may gather external or predefined knowledge about the analyzed game.

Useful game knowledge can include:

- boss names;
- miniboss names;
- locations;
- major NPCs;
- quests;
- chapters or acts;
- distinctive encounters;
- landmarks;
- game UI conventions;
- recognizable progression events;
- alternative names or spelling variants.

Keep game-specific knowledge separate from generic video-processing logic.

Avoid hard-coding knowledge about a particular game into reusable pipeline components.

Prefer structures such as:

- game profiles;
- knowledge files;
- metadata;
- configurable recognizers;
- retrieval-backed game context;

instead of game-specific conditional logic scattered throughout the application.

---

## 7. Generic Pipeline vs. Game-Specific Knowledge

Maintain a clear architectural distinction between:

### Generic processing

Components that should work for arbitrary games, such as:

- video conversion;
- frame extraction;
- sampling;
- scene detection;
- image preparation;
- model invocation;
- temporal aggregation;
- event scoring;
- chapter generation;
- caching;
- logging.

### Game-specific context

Information that describes a particular title, such as:

- Elden Ring boss names;
- locations;
- recognizable UI elements;
- chapter structures;
- game-specific event vocabulary.

A generic pipeline component should not need to know which particular game it is analyzing unless that information is explicitly passed through an abstraction designed for this purpose.

---

## 8. Long-Video Processing

The system is specifically intended for long videos.

Do not design algorithms under the assumption that the entire source video can cheaply be:

- loaded into memory;
- converted at full quality;
- analyzed frame-by-frame with an expensive model;
- sent to an AI model in one request.

Prefer scalable processing strategies.

Examples include:

- streaming;
- chunking;
- hierarchical analysis;
- configurable sampling;
- coarse-to-fine analysis;
- candidate detection followed by focused analysis;
- caching;
- incremental processing;
- resumable stages.

Processing a ten-hour video should not require restarting the entire pipeline because one late processing stage failed.

Where practical, expensive processing stages should produce reusable intermediate results.

---

## 9. Preserve Temporal Accuracy

Time information is critical.

Every intermediate representation that refers to a video event should preserve enough information to map the event back to the original source video.

Avoid unnecessary timestamp conversions that introduce drift or ambiguity.

Prefer explicit units and representations.

For example:

- original source timestamp;
- seconds as numeric values;
- frame number where meaningful;
- start/end intervals for detected events.

Do not rely only on formatted strings such as `01:32:17`.

Internal representations should remain machine-readable and unambiguous.

---

## 10. Chapter Generation

A detected event is not automatically a good YouTube chapter.

The chapter-generation stage should consider factors such as:

- significance;
- confidence;
- duration;
- temporal proximity to other events;
- duplication;
- usefulness to a viewer;
- chapter density;
- event hierarchy.

Avoid generating excessive micro-chapters.

Prefer a smaller number of meaningful chapters over a large list of noisy detections.

The system should preserve the distinction between:

1. raw detections;
2. interpreted gameplay events;
3. final chapter candidates.

Do not collapse these concepts into one data structure if doing so makes later reasoning or debugging difficult.

---

## 11. Confidence and Uncertainty

AI-based detection is inherently uncertain.

Do not represent uncertain predictions as unquestionable facts.

Where appropriate, detections should contain information such as:

- confidence;
- supporting evidence;
- detection source;
- alternative interpretation;
- temporal range.

Prefer explicit uncertainty over hidden heuristics.

When multiple evidence sources disagree, preserve enough information to investigate why.

---

## 12. Intermediate Data

Prefer structured intermediate representations.

Use machine-readable formats where appropriate, such as JSON or equivalent typed structures.

Intermediate artifacts should ideally be:

- deterministic where possible;
- inspectable;
- reusable;
- cacheable;
- versionable when formats evolve.

Avoid passing important pipeline information only through natural-language prompts if a structured representation is more appropriate.

---

## 13. Modularity

Prefer small components with clearly defined responsibilities.

Examples of potentially separate responsibilities include:

- source video inspection;
- video normalization;
- frame sampling;
- visual analysis;
- game knowledge retrieval;
- event detection;
- event aggregation;
- chapter generation;
- output formatting.

Do not create abstractions merely for theoretical purity.

Introduce abstractions when they provide one or more concrete benefits:

- clearer ownership;
- easier testing;
- alternative implementations;
- reduced coupling;
- reusable functionality.

---

## 14. Local-First Design

Project YCG is primarily intended as a **local video analysis system**.

Prefer designs that can operate locally when practical.

External cloud services may be supported where useful, but they should not unnecessarily become mandatory dependencies unless explicitly decided.

Be mindful that gameplay video files may be:

- very large;
- private;
- expensive to upload;
- slow to transfer.

Do not introduce automatic video uploads to external services without an explicit architectural decision.

---

## 15. Performance

Performance matters because the input can contain many hours of video.

Avoid obviously wasteful processing.

Before introducing an expensive operation, consider whether it can be:

- performed on reduced-resolution media;
- performed on sampled frames;
- cached;
- executed only on candidate regions;
- batched;
- parallelized safely;
- skipped when results already exist.

However, do not sacrifice detection quality purely for theoretical optimization.

Prefer measurable optimization over premature optimization.

---

## 16. Hardware Awareness

The system may use hardware acceleration when available.

Potential compute resources can include:

- CPU;
- GPU;
- hardware video decoder;
- hardware video encoder.

Keep hardware-specific implementations behind appropriate boundaries where practical.

Do not make the entire application depend on one specific GPU model unless explicitly required.

Graceful fallback paths are preferable where feasible.

---

## 17. AI Model Integration

Treat AI models as replaceable components.

Avoid coupling core domain logic directly to one model provider or model name unless necessary.

Model-specific adapters should isolate concerns such as:

- request formatting;
- image preparation;
- token/context limits;
- response parsing;
- retry behavior;
- model configuration.

Domain-level code should preferably operate on Project YCG concepts rather than provider-specific response objects.

---

## 18. Prompt Design

Prompts used by the system are part of application behavior.

Keep important prompts:

- version-controlled;
- understandable;
- testable where practical;
- separate from unrelated application logic.

Avoid assembling major prompts through large numbers of scattered string fragments.

Prompts should clearly distinguish:

- known facts;
- game knowledge;
- observed evidence;
- assumptions;
- requested output format.

When structured output is expected, define the expected schema explicitly.

---

## 19. Deterministic Code Before AI

Do not use an AI model for tasks that can be solved more reliably and cheaply with deterministic logic.

Examples may include:

- timestamp conversion;
- deduplication;
- sorting;
- interval merging;
- video metadata extraction;
- file management;
- validation;
- schema enforcement.

Use AI where interpretation or semantic understanding provides meaningful value.

---

## 20. Error Handling

Long-running pipelines must fail cleanly.

Prefer errors that identify:

- the failing processing stage;
- the affected source or chunk;
- the root cause where known;
- whether retrying is safe.

Do not silently swallow failures.

A failed analysis stage should not produce apparently valid chapter output without indicating that required information is missing.

---

## 21. Resume and Recovery

Where practical, long-running stages should support restart or resume behavior.

If several hours of video have already been processed successfully, a later failure should not unnecessarily invalidate all previous work.

Prefer persistent intermediate stage outputs when the cost of recomputation is significant.

---

## 22. Logging and Observability

Logs should help answer questions such as:

- What file is being processed?
- What pipeline stage is running?
- What time range is being analyzed?
- Which model or algorithm produced a detection?
- Why was a chapter candidate created or rejected?
- Where did a failure happen?
- How long did a processing stage take?

Do not flood logs with meaningless per-frame messages under normal logging levels.

Use appropriate log levels.

---

## 23. Configuration

Behavior likely to require experimentation should be configurable.

Examples include:

- sampling intervals;
- chunk size;
- model selection;
- confidence thresholds;
- candidate density;
- output paths;
- temporary storage;
- hardware acceleration;
- concurrency.

Do not expose every constant as configuration.

Configuration should represent meaningful operational or experimental choices.

---

## 24. Testing Philosophy

Prefer tests for behavior that matters.

Important areas include:

- timestamp mapping;
- interval handling;
- aggregation;
- chapter ordering;
- deduplication;
- configuration parsing;
- intermediate-data serialization;
- failure recovery;
- game-profile loading.

AI output itself may not always be deterministic.

Where AI behavior is involved, separate deterministic surrounding logic from model invocation so that as much as possible can be tested independently.

Use representative fixture data when useful.

Do not require multi-hour video processing for ordinary unit tests.

## 25. Test Assets

Keep test media small.

Do not commit large copyrighted gameplay recordings to the repository unless explicitly approved.

Prefer:

- short test clips;
- synthetic fixtures;
- generated metadata;
- user-provided local samples outside version control.

Document how larger integration-test media should be supplied when necessary.

## 26. Code Quality

Write code for maintainability first.

Prefer:

- meaningful names;
- explicit data models;
- small cohesive functions;
- clear boundaries;
- predictable control flow;
- useful types;
- straightforward implementation.

Avoid:

- unnecessary metaprogramming;
- speculative abstraction;
- clever code with hidden behavior;
- giant classes or functions;
- duplicated domain rules;
- unexplained magic constants.

Comments should explain **why**, not merely restate what the code does.

## 32. Avoid Premature Product Expansion

Implement the requested capability before expanding the scope.

Do not spontaneously turn Project YCG into:

- a video editor;
- a YouTube uploader;
- a streaming platform;
- a general-purpose media management system;
- a full game database;
- a cloud SaaS platform.

Keep the core goal focused:

> Understand long-form gameplay video well enough to generate useful chapter information.

---

## 33. Do Not Hide Heuristics

When implementing heuristic behavior, make the reasoning discoverable.

For example, if events closer than a certain threshold are merged, the rule should be represented clearly in code or configuration.

Avoid unexplained behavior embedded in arbitrary constants.

---

## 34. User Review

Project YCG should assist the creator rather than assume perfect automation.

Where appropriate, architecture should allow the generated chapter list to be inspected or modified before final use.

Do not assume every AI-generated chapter should automatically become final output.

---

## 35. Output Integrity

Generated output must preserve chronological order.

Do not create:

- negative timestamps;
- timestamps beyond the source duration;
- overlapping chapter semantics without intentional handling;
- duplicate chapters representing the same event;
- malformed YouTube timestamps.

Final output generation should validate its inputs.

---

## 36. Security and Privacy

Treat analyzed videos as potentially private user data.

Avoid transmitting:

- video frames;
- transcripts;
- filenames containing private information;
- extracted metadata;

to external services unless that behavior is explicitly part of the chosen architecture and clearly controlled.

Never place credentials directly in source code.

Use appropriate configuration or environment-based secret handling.

## 38. Before Implementing a New Feature

Before implementing a significant new feature, determine:

- which milestone it belongs to and whether it is within that milestone's documented scope;
- which accepted ADRs constrain the implementation;
- where it belongs in the pipeline;
- what its input is;
- what its output is;
- whether the output should be persisted;
- whether it is generic or game-specific;
- whether deterministic logic can solve part of the problem;
- how it can be tested;
- how failures can be diagnosed.

If these remain unclear after reading the specification, applicable ADRs, and milestone document, identify the ambiguity rather than inventing major product requirements.

## 43. Guiding Engineering Principle

When choosing between two implementations, prefer the one that makes the analysis pipeline:

- easier to understand;
- easier to inspect;
- easier to test;
- easier to resume;
- easier to replace individual AI components;
- easier to debug when the generated chapter list is wrong.

Project YCG is an AI-assisted system, but its behavior should remain as observable and controllable as practical.

---

## 44. Final Reminder

Always keep the central use case in mind:

> A creator may provide many hours of gameplay footage. Project YCG should efficiently analyze that footage, understand recognizable gameplay events using primarily visual evidence and reliable game knowledge, and produce useful, reviewable YouTube chapter suggestions.

Do not optimize the architecture for short demo videos at the expense of this real-world use case.
